# COPILOT-FIX (2026-10-04) - "Change all the pink on the car to tangerine orange"

Owner test: ARCA Chevrolet SS PSD, pink painted by ZONES (holo side zones, number fill, a layer zone: base colour #ff3fa4) over a yellow / seafoam paint. Result: a minute of dots, pink -> orange for 2 s, then almost the whole car orange, then the critic undid it ("only 0.8% of the visible paint is pink"), footer `$0.028 · claude-haiku-4.5 · 6 calls · fixed with claude-haiku-4.5`.
Test server 59879 only, own Chrome CDP 9691 (`_easy_claude_work/pw/chrome_up_9691.py`). Evidence: `_easy_claude_work/eval/copilot_fix/` (`*.json` = zones before/after, tool trail, every /api/ai/chat call with its model, progress lines; `*_before.png` / `*_after.png` = live preview with Wire / Mask / Car Mandatory hidden + `_finishLayerVisibilityChange()`; `owner_before_after.png`). Scripts: `pw/copilot_fix_common.py` (owner-like zones), `pw/copilot_fix_repro.py <tag> offline|owner|online ["sentence"]` (`COPILOT_EMU=gear|novision` emulates the new route on the old test server), `pw/copilot_fix_route_test.py` (route unit test, no network). Spend: about $0.03 (5 DeepSeek runs; shared ledger went $0.028 -> $0.057).

## Root causes
1. **Wrong models.** `js/spb-pro-ai.js` `escModel()` defaulted the repair turn to `anthropic/claude-haiku-4.5`; `CRITIC_MODEL = 'qwen/qwen3.7-plus'` judged the picture (retrying on the server's default vision model); `server_routes/ai_copilot_routes.py` honoured any client `model`, sent pictures to `visionModel` (deepseek-v4-flash-vision-exp) and fell back to `qwen/qwen3.7-flash`. The footer printed only the LAST model.
2. **"The pink" = the flattened paint.** `describe_paint` / `editEnv` read `Z.paintColours` (the source pixels: yellow, seafoam ... pink 0.8%) and never the colours the zones paint. The edit brain recoloured the paint's own magenta pixels (2%) and left the four pink zones pink (repro `before_owner.json`: refinish "hot pink" + "magenta" -> `#c908c7`, pink zones unchanged, reply falsely claimed the number fill changed). The post-apply check then demanded PINK be visible (`wantedColours` counted the colour being changed FROM), the haiku repair painted the car orange, the critic undid it. Also "tangerine" was an unknown look word, so the built-in brain declined and the request went to the AI at all.
3. **Progress.** The bubble showed one static phrase ("Reading your paint and your request…") through the whole AI turn; nothing between turn, apply and check.

## Fix
- **Models (one = the gear's):** server uses the gear `model` for every call; a client-requested model is ignored + logged unless it equals `settings.escalateModel` (explicit opt-in via `/api/ai/settings`, reported by `/api/ai/status`, empty by default); picture calls on a model that cannot read pictures return `error:'no_vision'` at no cost (catalogue check, or upstream image rejection); vision fallback removed; status `visionModel` = gear model, + `modelSeesPictures`, `escalateModel`; failures logged with their model. Client: `CRITIC_MODEL` removed, critic sends no model, `no_vision` -> critic skipped, measured checks decide alone, reply note + footer "checked by the app (no vision model)"; `escModel()` = the server opt-in only (the hidden localStorage `spb_pro_ai_escalate` is retired); the footer lists every model with its call count (main turn, tool pictures, critic, repairs).
- **Zone colours:** `editEnv` adds `zoneColours` (solid zone colours that select something: hex, zone, id, coverage %, layers) and `shown_pct` per paint colour (how much still shows after recolouring zones); `describe_paint` returns `colours_painted_by_zones` + a note; rule 16d tells the model. `spb-pro-edit.js` `compile`: a colour target that matches zone colours (family) emits one zone EDIT per zone (`_meta.zoneEdit`: colour / look / shade, the zone keeps its selection and finish unless a look is named); paint pixels of that colour are added only when >= 2% still shows; a colour < 2% that no zone paints ASKS (chip "... anyway" does it); no match + zone colours -> ask listing both. `queueEditZones` applies zone edits via edit_zone. Online `refinish` gets the same env + rule, new `layer` / `anyway` params.
- **Layer scope:** "in the Numbers layer, all the pink to metallic silver" / "all the pink in the Numbers layer ..." / "make the Numbers layer gold": `layerScope()` matches real layer names (and role words) BEFORE parsing, so "layer" is never the look "Layered Cut Foil"; colour targets get `layers`, a bare layer = a layer target. Unknown layer -> ask with the layer list.
- **Source colours are not "wanted":** `sourceColours()` ("X to Y", "X on the car to Y", "replace X with", "from X", edit-brain colour targets) are dropped from the post-apply visibility check.
- **tangerine / mandarin / pumpkin ...** map to hexes (reply says "tangerine").
- **Progress:** "<step label> · step k of 4 · N s" (3 steps for the built-in brain), ticking every second, kept across the AI-turn -> check gap: Reading your paint -> Planning (AI round n) -> Applying N changes · rendering the preview -> Checking the result · looking at the preview -> Fixing ... The chat studio reuses this bubble (no studio code changed).
- Also: `editPlan` yields "those are not the numbers" to the element-wrong handler (t259 B was failing).
